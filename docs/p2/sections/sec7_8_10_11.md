## 7 Design Rationale

### 7.1 Architecture decision records

#### ADR-01  Layered three-tier architecture with event-driven messaging

| Field | Content |
| --- | --- |
| Status | Accepted |
| Date and owner | Nov 7, 2026 · Jarir Ali |
| Context (drivers) | QAS-01 (order on the KDS within 5 s), QAS-02 (customer pages within 3 s for 100 concurrent users), QAS-03 (no confirmed reservation or order lost across a restart) and CON-02 (touch-only KDS). |
| Options considered | (1) Layered three tiers (presentation, business logic, persistence) with event-driven messaging to the KDS. (2) Microservices, scaling reservation and order processing independently. (3) Shared repository, with every client reading state from one database. |
| Decision | Option 1, as analysed in section 6.2. |
| Consequences | Favors performance and reliability (QAS-01, QAS-02, QAS-03). Move: separate the presentation, business and data tiers, and push kitchen events instead of reading the database. Cost: an event broker must be deployed alongside the tiers, and clients must handle reconnections. Microservices were rejected for their distributed-system overhead; the shared repository for polling latency and lock contention. |
| Evidence | Spike S-01 (section 8): event push met QAS-01 on degraded Wi-Fi, while polling, the shared repository's access pattern, delivered only 82% of orders within 5 s. |
| Related | ADR-02, ADR-03, QAS-01, QAS-02, QAS-03, R6 |

#### ADR-02  Push kitchen orders to screens over WebSocket instead of polling

| Field | Content |
| --- | --- |
| Status | Accepted |
| Date and owner | Nov 7, 2026 · Manideep Pendyala |
| Context (drivers) | QAS-01 (order on the KDS within 5 s for 95% of orders), UC-05 with FR-09 and FR-11, and A1 (restaurant Wi-Fi is the only link between front and back of house). |
| Options considered | (1) KDS and server screens poll the order service every 3 s. (2) The order service pushes each new order and status change over a persistent WebSocket connection. |
| Decision | Option 2, WebSocket push. After a reconnect, a screen requests the orders it missed. |
| Consequences | Favors performance (QAS-01). Move: replace polling with server push. Cost: the order service must manage open connections and reconnects, and a screen that drops off the Wi-Fi depends on its catch-up request (R6). |
| Evidence | Spike S-01 (section 8): on degraded Wi-Fi, push delivered 100% of orders within 5 s; polling delivered 82%. |
| Related | ADR-03, QAS-01, R6 |

#### ADR-03  Save every order to the database before notifying any screen

| Field | Content |
| --- | --- |
| Status | Accepted |
| Date and owner | Nov 7, 2026 · Manideep Pendyala |
| Context (drivers) | QAS-03 (all confirmed reservations and submitted orders survive a restart), FR-03 (no overlapping table allocation), and the UC-05 minimal guarantee (a failed submission leaves no kitchen entry). |
| Options considered | (1) Keep the kitchen queue in the order service's memory and save it to the database in the background. (2) Save each order in a PostgreSQL transaction first, then notify screens. |
| Decision | Option 2. PostgreSQL is the single source of truth; screens are notified only after the save commits. |
| Consequences | Favors reliability (QAS-03). Move: commit before notify. Cost: a database write is added to the QAS-01 path, and the database becomes a single point of failure (R7). |
| Evidence | None yet. S-01 kept orders in memory; open question Q5. |
| Related | ADR-02, QAS-01, QAS-03, R7 |

### 7.2 Trade-off summary

| Quality favored | Architectural move | Cost accepted | Recorded in |
| --- | --- | --- | --- |
| Performance and reliability (QAS-01, QAS-02, QAS-03) | Layered tiers with event-driven messaging instead of microservices or a shared repository | An event broker to deploy and run; clients handle reconnections | ADR-01 |
| Performance (QAS-01) | Server push over WebSocket instead of polling | Connection and reconnect handling on the order service | ADR-02 |
| Reliability (QAS-03) | Commit to the database before notifying any screen | Extra latency on the order path; the database is a single point of failure | ADR-03 |

## 8 Prototype Evidence: Architecture Spike

| Field | Content |
| --- | --- |
| Spike ID and title | S-01  Push vs polling for kitchen order delivery |
| Risk or decision it addresses | R6 / ADR-02 / QAS-01 |
| Question (answerable yes or no) | Does pushing orders over a WebSocket put 95% of 50 orders from 20 tables on the KDS within 5 s, and does polling every 3 s also do so? |
| Set-up | Node.js 24 with the ws library; orders kept in memory. One script runs the order service, a push KDS, a polling KDS and 20 simulated tables submitting 50 orders over 30 s. Wi-Fi is simulated as 5–80 ms per hop; normal Wi-Fi stalls 2% of hops by 1 s, degraded Wi-Fi stalls 20% of hops by 2 s. Folder: /spikes/S-01/. |
| How it was measured | For each order, KDS receive time minus submit time on one clock; p50, p95 and the share within 5 s. |
| Result (numbers) | Normal Wi-Fi: push p95 138 ms, polling p95 2997 ms; both 100% within 5 s. Degraded Wi-Fi: push p95 4082 ms, 100% within 5 s; polling p95 6188 ms, 82% within 5 s. |
| What it changed or confirmed | Confirmed ADR-02: only push meets QAS-01 on degraded Wi-Fi. |
| Where to see it | Commit 30be6d7; /spikes/S-01/ (README.md, results-nominal.json, results-degraded-wifi.json) |
